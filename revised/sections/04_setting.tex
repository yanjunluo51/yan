\section{Decision setting and model inputs}

The member-threshold vector answering these gaps is built from the gate decision and its inputs. These inputs are of two kinds: inputs shared by all members and one recorded weight per member. Each reported threshold combines the shared model inputs with the weight of one member.

\subsection{The gate-level decision problem}

At each gate of a stage-gate sequence, the project receives one invest-or-wait classification per member before the committee makes its collective decision. The committee also declares an interval of forward volatilities, the ambiguity set of the gate, which Eq.~(\ref{eq:ambset}) parameterizes by one radius around an anchor. Members share one regulatory information set and differ only in the weight $\alpha_i\in[0,1]$ recorded for member $i$ on the adverse endpoint.

The shared inputs are a calibration $\theta=(r,\mu_c,\sbar)$, the project inputs $I$ and $Q$, the declared ambiguity radius $h_t$, and the prevailing price $P_t$. The member-specific inputs are the recorded weights $\{\alpha_i\}_{i=1}^{m}$. From these inputs, the method returns the member-specific price thresholds and classifies the gate at $P_t$ as unanimous wait, mixed, or unanimous invest. It also states whether the affine report may be released alone or requires a benchmark recomputation.

Figure~\ref{fig:architecture} organizes these inputs and outputs into an input layer, an analytical layer, and an interface layer. The interface layer applies the release rule and issues either an affine-only report or a dual report containing both the affine and the benchmark results.

\subsection{Model inputs and assumptions}

The analysis rests on three maintained model assumptions, one reporting convention, and one application-side input. (i) Forward volatility carries the ambiguity, and drift is held fixed. (ii) Standard deviation parameterizes the ambiguity set. (iii) The carbon-price process follows a GBM with $r>\mu_c>0$. The reporting convention is the affine endpoint rule, which defines the member triggers, and the application-side input is the ambiguity radius. Within a gate, the common information set stays fixed, and so do the recorded weights, which are reporting inputs registered in advance. Each member then receives a separate invest-or-wait classification.

Under assumption (i), ambiguity concerns the width of the forward distribution and leaves its mean unaffected. The policy-text signal of the application fits this reading, because it records variation in semantic dispersion and carries no information about the direction of policy. The signal therefore configures the ambiguity radius, and the growth scenario $\mu_c$ stays fixed. The available record left the scale of the signal-to-radius map unsettled, so this map is treated as a convention. Forward volatility enters as a single parameter, and assumption (ii) declares its ambiguity set in standard-deviation units. This declaration fixes the coordinate for evaluating trigger curvature and, with it, the sign of the critical-weight displacement.

The ambiguity radius enters the model as a single number per gate. The forward-volatility anchor $\sbar$ and an admissibility margin $\epsilon\in(0,1)$ fix its admissible range. The anchor stays fixed across gates within an application. The radius of each gate is capped at $(1-\epsilon)\sbar$, which keeps the lower volatility endpoint strictly positive. The ambiguity set is
\begin{equation}
\sigma_p\in\Sigma_t=[\sbar-h_t,\;\sbar+h_t],
\label{eq:ambset}
\end{equation}
where $\sigma_p$ denotes forward volatility. A committee may declare the gate radius $h_t$ directly or derive it from an auxiliary series, as in the application. Radii quoted as percentages are relative radii $h_t/\sbar$. The primary radius range covers relative radii up to 22\%, and the extended range adds a 33\% stress radius. Every numerical result is evaluated on a finite grid, and its scope is stated with the result.

With these definitions, all members share the calibration, the project inputs, the ambiguity set, and the prevailing price, and each member carries one recorded weight. The remaining task is analytical: mapping each weight to a trigger, converting the triggers into price thresholds, and stating when the report may be released.
